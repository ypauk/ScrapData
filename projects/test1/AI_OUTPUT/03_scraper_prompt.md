# КОНТЕКСТ ПРОЕКТА

## Анализ (этап 1)

## 1. Краткое описание задачи


Клиент хочет получить скрейпер для сайта `professionele-koeling.nl`, который собирает данные о товарах из категории **Koelkasten&Kisten**.


На текущем этапе требуется **тестовая выгрузка только 2 товаров**. После подтверждения теста предполагается масштабирование на весь необходимый объём.


Ключевое требование — итоговый JSON должен строго соответствовать структуре `DS-PRK-Scraper.json`: не добавлять, не удалять, не переименовывать и не объединять поля.


Для каждого товара необходимо собрать:



- URL;

- Breadcrumb;

- Title;

- Short description;

- URL всех изображений;

- имена изображений;

- обычную цену;

- Sale price;

- полное текстовое Description;

- Specs;

- отдельные характеристики из `Spec_detail`, где текст до `:` является названием характеристики.


При отсутствии скидки `Sale price` должен оставаться пустым. Отсутствующие характеристики также оставляются пустыми. HTML из описания в результат не включается — нужен чистый текст.


Отдельно клиент требует **скачивать изображения**, а не только сохранять их URL.


По предоставленным данным сайт имеет пагинацию и сейчас категория содержит **429 товаров**, по 36 на странице. Это существенно больше, чем текущий тест из 2 товаров. Professionele Koeling


**Уровень уверенности: высокий** относительно структуры данных и текущего поведения категории; средний относительно внутренней реализации сайта.



## 2. Какой конечный результат нужен


Основной результат:


**JSON**, содержащий данные о товарах строго в структуре, заданной `DS-PRK-Scraper.json`.


Дополнительно должны быть скачаны изображения товаров.


Важно:



- порядок полей должен соответствовать спецификации;

- каждое поле должно находиться отдельно;

- характеристики нельзя складывать в одну общую колонку;

- отсутствующие значения должны быть пустыми;

- HTML-разметка Description не сохраняется.


На текущем этапе ожидается тестовая выдача на **2 товара**.



## 3. Как лучше решить задачу


### Рекомендуемый подход: PlaywrightEngine + парсинг HTML


Использовать предоставляемый проектом **PlaywrightEngine** для открытия страниц и получения уже отрендеренного DOM, после чего извлекать данные из HTML.


Это наиболее подходящий вариант по нескольким причинам:



- В проекте уже зафиксировано использование `PlaywrightEngine` для `scraper.py`, поэтому менять базовый механизм на `requests` нецелесообразно.

- В исходных заметках указано, что сайт использует JavaScript.

- При этом фактическая текущая страница уже содержит товарные данные в доступном HTML: названия, ссылки, цены и пагинацию. Professionele Koeling

- Значит, Playwright обеспечивает надёжное получение страницы, а дальнейший парсинг можно держать максимально простым.

- Для полной карточки товара потребуется переход на product URL, поскольку category page не содержит всех требуемых полей — например, полного Description, Breadcrumb и характеристик.


### Оптимальный поток


**Category page → получить URL товаров → открыть product page → извлечь требуемые поля → скачать изображения → сформировать JSON.**


Для текущего теста достаточно обработать 2 товара.


Наиболее простой вариант — взять первые два товара категории, **но это необходимо подтвердить**, поскольку в спецификации не указано, какие именно два товара клиент хочет использовать для теста.



## 4. Почему остальные варианты хуже


### requests + BeautifulSoup


Не рекомендую как основной механизм.


Для обычного HTML это было бы проще, однако проект уже использует PlaywrightEngine, а исходные данные указывают на JavaScript-сайт. Дополнительное переключение механизма получения страниц не даст преимущества, достаточного для изменения предусмотренного проектом подхода.


При этом **BeautifulSoup-подобный HTML parsing как концепция после получения DOM вполне уместен**, если он уже предусмотрен существующим стеком проекта.


### Scrapy


Избыточен для задачи текущего масштаба.


429 товаров — не настолько большой объём, чтобы ради него добавлять полноценный scraping framework, особенно если инфраструктура проекта уже предоставляет PlaywrightEngine.


### Selenium


Не даёт преимуществ перед уже выбранным PlaywrightEngine и добавляет ненужную замену технологии.


### Прямой API


На основании предоставленного `network.har` API обнаружить нельзя: файл фактически пустой.


Кроме того, в `notes.txt` прямо указано, что API нет.


Поэтому строить решение вокруг API сейчас оснований нет.


### GraphQL


Признаков GraphQL в предоставленных материалах нет.


### Только category pages


Недостаточно.


Category page содержит URL, название и цены, но не все необходимые поля. Например, предоставленная product page для Polar GE579 содержит short description и цены, а полное описание и характеристики должны находиться дальше в карточке товара. Поэтому переход на product pages необходим для полного соответствия спецификации.

## 7. Возможные сложности


### 1. Cloudflare


Самый существенный технический риск.


Есть `cf_clearance`, поэтому при автоматизации возможно:



- истечение cookie;

- появление challenge;

- временная блокировка;

- изменение Cloudflare-поведения.


### 2. JavaScript


Даже несмотря на наличие данных в HTML, часть функциональности сайта может зависеть от браузера. Именно поэтому Playwright остаётся предпочтительным способом получения страниц.


### 3. 429 товаров


Полная задача потенциально означает обработку 429 товаров, а не 2.


Это требует корректной обработки пагинации и аккуратного темпа запросов. Professionele Koeling


### 4. Различия между товарами


Не у каждого товара обязательно будут заполнены все характеристики.


По требованиям клиента такие поля должны оставаться пустыми, а не заполняться догадками.


### 5. Структура характеристик


`Spec_detail` требует преобразования текста вида:


`Artikelnummer: GE579`


в отдельное поле с заголовком `Artikelnummer`.


Это потенциально чувствительное место, потому что реальные товары могут иметь:



- разные наборы характеристик;

- одинаковые названия характеристик;

- несколько значений;

- нестандартные строки без `:`.


Нельзя заранее придумывать правила, которых нет в спецификации.


### 6. Изображения


У товара может быть несколько изображений. Их необходимо сохранять отдельно, а в JSON — согласно правилам `imageurl` и `image_name`, через запятую.


### 7. Изменение HTML


Сайт может изменить CSS-классы или структуру product page.


Риск умеренный.


### 8. Несоответствие checkpoint


Предоставленный `checkpoint.json` говорит о `processed_count: 49`, тогда как текущая категория показывает 429 товаров. Это не обязательно ошибка: checkpoint явно относится к конкретному предыдущему запуску (`run_20260813_053013`), поэтому его нельзя автоматически трактовать как актуальное состояние всего сайта.

## 10. План разработки


### Этап 1 — тестовое получение двух товаров


**Цель:** проверить доступность category page и product pages через существующий PlaywrightEngine.


**Результат:** получены две карточки товаров.


**Зависимости:** рабочий PlaywrightEngine и доступ к сайту.



### Этап 2 — извлечение данных


**Цель:** получить все поля, предусмотренные `DS-PRK-Scraper.json`.


**Результат:** две полностью заполненные записи с пустыми значениями там, где данных нет.


**Зависимости:** корректно загруженные product pages.



### Этап 3 — изображения


**Цель:** скачать все изображения каждого тестового товара.


**Результат:** локальные image files + соответствующие `imageurl`/`image_name` в JSON.


**Зависимости:** доступность image URLs.



### Этап 4 — проверка структуры JSON


**Цель:** убедиться, что результат строго соответствует спецификации.


**Результат:** тестовый JSON без лишних или отсутствующих полей и без смешивания нескольких характеристик в одном поле.


**Зависимости:** результаты этапов 2–3.



### Этап 5 — передача тестового результата клиенту


**Цель:** получить подтверждение корректности двух товаров.


**Результат:** согласованный формат данных.


**Зависимости:** готовый тестовый JSON.



### Этап 6 — масштабирование


**Цель:** после подтверждения перейти от 2 товаров к согласованному полному объёму.


**Результат:** полный JSON и изображения.


**Зависимости:** подтверждение клиента и определённый полный scope.

- подключать API;

## 13. Итоговая рекомендация

- соответствует зафиксированной архитектуре проекта;

# Проектирование scraper для professionele-koeling.nl

## 0. Выбранный подход

Выбираю **PlaywrightEngine + HTML + BeautifulSoup**.

API использовать не следует: в материалах проекта прямо указано, что API отсутствует, а `network.har` пуст. При этом framework уже принудительно предоставляет `PlaywrightEngine`, включая browser context, cookies, proxy и user-agent. Поэтому добавление `requests`, `httpx`, Selenium или отдельного API-клиента нарушило бы архитектурный контракт проекта.

### Почему Playwright

**Плюсы:**

- соответствует существующему framework;
- корректно работает с JS-сайтом;
- использует уже предоставленный browser context;
- позволяет получать итоговый HTML после browser rendering;
- подходит для потенциального Cloudflare challenge;
- не требует новой сетевой архитектуры.
**Минусы:**

- тяжелее обычного HTTP-клиента;
- медленнее;
- наличие Cloudflare повышает operational risk;
- большое число переходов на product pages увеличит длительность полного scrape.
Для текущего теста на 2 товара эти недостатки несущественны.

## 2.2. Алгоритм scrape_data(engine)

### Тестовый режим

- Использовать category URL:`https://www.professionele-koeling.nl/koelkasten-kisten.html`
- Получить rendered HTML через `_fetch_listing_html()`.
- Передать HTML в `_extract_product_urls()`.
- Получить URL товаров в порядке их появления.
- Взять первые **2 URL**.
- Для каждого URL:

- сделать небольшую паузу через существующий `random_delay()`;
- открыть product page;
- дождаться загрузки страницы;
- получить итоговый HTML;
- добавить HTML в результирующий список.
- Вернуть `List[str]` из двух product HTML.
Таким образом, в `parse_html_data()` будут поступать именно страницы товаров, а не category HTML. Это упрощает идентификацию типа документа и исключает необходимость смешивать listing parser и product parser.

### Full scrape

Для production/full scrape алгоритм расширяется:

- Открыть страницу категории.
- Извлечь product URLs.
- Добавить URL ещё не обработанных товаров.
- Перейти к следующей странице.
- Повторять до отсутствия `next` URL.
- Не фильтровать товары по наличию.
- Для каждого уникального product URL получить HTML.
- Вернуть HTML product pages в `List[str]`.
## 2.3. Pagination

Использовать **URL pagination**, а не infinite scroll и не клик как основной механизм.

В предоставленном HTML есть:

- текущая страница `1`;
- `?p=2`;
- `?p=3`;
- `?p=4`;
- `?p=5`;
- ссылка `next` на `?p=2`.
Поэтому `_get_next_page_url()` должен:

- искать блок `.pager .pages`;
- искать ссылку `.next a`;
- получить её `href`;
- нормализовать URL относительно `current_url`;
- вернуть URL;
- если `.next a` отсутствует — вернуть `None`.
**ПРЕДПОЛОЖЕНИЕ:** для всего каталога структура pagination остаётся такой же, как в предоставленном HTML. Для теста это предположение практически не влияет на результат, поскольку нужны только первые два товара.

Не следует заранее рассчитывать количество страниц как `ceil(429 / 36)`: число 429 является наблюдаемым значением из текущего HTML, но для production правильнее ориентироваться на фактическую ссылку `next`.

## 2.4. Навигация и ожидание страницы

На category page достаточно дождаться появления:

`ul.products-grid.category-products-grid`

и/или

`li.item`

На product page — основного product container и `h1` внутри `.product-name`.

Из предоставленного HTML подтверждены следующие селекторы:

- `.products-grid li.item`
- `.product-image a.product-image`
- `.product-name a`
- `.pager .pages`
- `.pager .pages .next a`
- `.breadcrumbs`
- `.product-name h1`
- `.short-description`
- `.price-box`


**Lazy loading:** подтверждения нет. Поэтому не добавлять обязательный scroll без доказательства необходимости.

**Tabs / "Показать ещё":** в предоставленном product HTML таких элементов не обнаружено. Не добавлять клики, пока реальные страницы не покажут необходимость.

## 2.5. random_delay()

Использовать уже существующий `app.utils.random_delay()`:

- после загрузки category page перед обращением к product pages;
- между переходами на product pages;
- между category pages при полном scrape.
Не создавать собственный delay-механизм.

Параллельный массовый обход не использовать: наличие `cf_clearance` показывает, что Cloudflare является реальным operational risk.

# 3.2. Спецификация полей

Финальный словарь должен содержать **строго следующие имена и порядок полей**:

- `URL`
- `Breadcrumb`
- `Title `
- `Short description`
- `imageurl`
- `image_name`
- `Price`
- `Sale price`
- `Description `
- `Specs`
- `Spec_detail`
Пробелы в `Title ` и `Description ` являются частью авторитетной спецификации и должны сохраниться. Нельзя превращать их в `Title` и `Description`.

### URL

Источник:

- URL текущей product page.
Значение должно быть абсолютным URL.

**Не брать URL category page.**

### Breadcrumb

Источник:

`.breadcrumbs`

Из предоставленного HTML:

`Home → Koelkasten&Kisten → Polar GE579`

Спецификация требует поле `Breadcrumb`, поэтому сохранять следует breadcrumb товара как единое текстовое значение, а не создавать дополнительные поля.

**ПРЕДПОЛОЖЕНИЕ:** разделитель между уровнями breadcrumb должен быть выбран единообразно, например `>`. Сам prompt не задаёт конкретный разделитель.

### Title

Источник:

`.product-name h1`

Для предоставленного товара:

`Polar GE579`

Если элемент отсутствует — `""`.

### Short description

Источник:

`.short-description .std`

Нужно извлечь пользовательский текст без HTML.

При этом promotional block:

`Advies nodig, of meerdere stuks...`

не следует автоматически считать частью short description.

**ПРЕДПОЛОЖЕНИЕ:** short description — это основное описание товара в первом `<p>`, а не рекламный контактный блок. Это требует проверки на реальных тестовых страницах.

Переносы `<br>` преобразовывать в пробелы/переносы строк последовательно, без сохранения HTML.

### imageurl

Извлекать URL изображений товара из соответствующего product image gallery.

Если изображений несколько — сохранять значения согласно инструкции спецификации: **разделять запятыми**.

В category HTML подтверждён `<img src="...">`, но предоставленный product HTML обрывается до блока изображений. Поэтому точный product-gallery selector пока неизвестен.

**ПРЕДПОЛОЖЕНИЕ:** URL изображения будут находиться в `img[src]` внутри product image/gallery container.

### image_name

Для каждого image URL определить имя файла из URL.

Например:

`.../polar_dm071_glasdeurkoelkast_46_liter.jpg`

→

`polar_dm071_glasdeurkoelkast_46_liter.jpg`

При нескольких изображениях имена разделяются запятыми в том же порядке, что и `imageurl`.

### Скачивание изображений

Это отдельная важная граница ответственности.

Изображения **не должен скачивать parser**, потому что parser запрещено использовать для сетевых запросов.

Их скачивание должно выполняться в `scraper.py` через предоставленный browser/network механизм **как сетевой side effect**, при этом основной контракт `scrape_data(engine) → List[str]` не изменяется.

Однако здесь есть нерешённая проблема: спецификация не определяет, должен ли `imageurl` после скачивания содержать:

- исходный URL;
- локальный путь;
- оба значения.
Поэтому самостоятельно менять смысл `imageurl` нельзя.

### Price

Для HTML:

`.price-box .old-price .price`

В предоставленном примере:

`€ 255,99`

→ `255.99`

Для нормализации использовать существующий `app.utils.clean_price()`, а не создавать собственный price parser.

Если обычная цена отсутствует:

`None` или `""` — выбрать значение, согласованное с фактическим контрактом exporter; при отсутствии такого указания безопаснее использовать `None`.

### Sale price

Источник:

`.price-box .special-price .price`

Для примера:

`€ 229,00` → `229.00`.

Если `.special-price` отсутствует, поле должно быть **пустым**, а не копировать `Price`. Это явно подтверждено требованиями клиента.

### Description

Источник — полный product description.

Нужно:

- взять HTML блока полного описания;
- удалить HTML markup;
- сохранить весь текст;
- нормализовать лишние пробелы;
- сохранить логические переносы строк;
- не удалять характеристики, если они являются частью полного description.
HTML-разметка в результате запрещена: клиент запросил именно текст.

**ПРЕДПОЛОЖЕНИЕ:** конкретный selector полного description нельзя достоверно назвать по предоставленному фрагменту, поскольку product HTML заканчивается после блока цены. Его необходимо определить на полном сохранённом product HTML.

### Specs

Это наиболее неоднозначное поле.

В `DS-PRK-Scraper.json` находится инструкция:

`if multipli seperated by comma ... each own colom`

а `notes.txt` прямо говорит, что это **инструкция по заполнению**, а не повреждённые данные.

Следовательно:

- не удалять `Specs`;
- не превращать его произвольно в одно длинное поле;
- не объединять разные характеристики;
- каждую характеристику обрабатывать отдельно согласно фактической структуре specification.
Но точный формат JSON для `Specs` **не определён достаточно однозначно**: предоставлен screenshot reference, но не machine-readable пример структуры.

Поэтому окончательную вложенную структуру `Specs` самостоятельно придумывать нельзя.

### Spec_detail

Правило спецификации:

всё до `:` является header.

То есть для:

`Artikelnummer: GE579`

header:

`Artikelnummer`

value:

`GE579`

Аналогично:

`Inhoud: 29 liter`

→ header `Inhoud`, value `29 liter`.

Если одна характеристика встречается несколько раз, как:

`Temperatuurbereik: ...`

её нельзя молча объединять с другой характеристикой или терять одно из значений.

Отсутствующие характеристики оставлять пустыми согласно требованиям клиента.

# 3.3. Финальная структура результата

Один parsed product должен иметь следующую форму:

```
{
    "URL": "...",
    "Breadcrumb": "...",
    "Title ": "...",
    "Short description": "...",
    "imageurl": "...",
    "image_name": "...",
    "Price": ...,
    "Sale price": ...,
    "Description ": "...",
    "Specs": ...,
    "Spec_detail": ...
}
```

Это **псевдоструктура, а не Python-код**.

Никаких дополнительных полей вроде `sku`, `availability`, `currency`, `download_path` или `category` добавлять нельзя, поскольку клиент их отдельно не запросил.

# 5. Оценка рисков

- **Cloudflare** — подтверждён потенциальный риск: в cookies присутствует `cf_clearance`.
- **Login** — обязательная авторизация не подтверждена.
- **Rate limiting** — явный лимит не обнаружен, но aggressive scraping потенциально опасен из-за Cloudflare.
- **CAPTCHA** — наличие не подтверждено.
- **Infinite Scroll** — не обнаружен; есть обычная pagination.
- **Shadow DOM** — не обнаружен.
- **iframe** — не обнаружен.
- **WebSocket** — признаков нет.
- **GraphQL API** — признаков нет.
- **Изменение DOM** — средний риск, поскольку selectors зависят от текущего frontend.
- **Различия product templates** — существенный риск: представлен только один product HTML.
- **Изображения** — точный product-gallery HTML не предоставлен.
- **Specs** — точная JSON-структура неоднозначна.
- **JSON container** — не определено, должен ли итоговый JSON быть массивом объектов или иметь дополнительный wrapper.
Первые два товара должны быть использованы именно как structural validation перед масштабированием.

# 6. Что остаётся неизвестным

Это принципиально важно: неизвестные значения нельзя компенсировать выдуманными selectors или структурой данных.

### 1. Полный HTML второго товара

Предоставлен только один фрагмент product page. Поэтому нельзя гарантировать, что второй товар имеет тот же DOM.

### 2. Selector полного description

В предоставленном product HTML видны breadcrumb, title, short description и price, но полный description/specification block отсутствует.

### 3. Selector product image gallery

В category HTML есть image selector, но полноценный product gallery не представлен.

### 4. Точный формат Specs

Specification содержит инструкцию `each own colom`, но не предоставляет полноценный machine-readable пример результата.

### 5. Значение imageurl после скачивания

Не определено, должен ли там находиться исходный URL или локальный путь к скачанному файлу.

### 6. Расположение скачанных изображений

Не определено, должны ли файлы находиться:

- рядом с JSON;
- в отдельной директории;
- в директории, заданной framework.
`config.py` уже владеет путями, поэтому самостоятельно создавать новую конфигурацию нельзя.

### 7. Верхний JSON container

Не определено, должен ли результат быть:

`[product1, product2]`

или объектом с вложенным списком.

Это нужно подтвердить до финального export, поскольку `DS-PRK-Scraper.json` показывает структуру **одного товара**, но не container для нескольких товаров.

### 8. Полная pagination для production

Из предоставленного HTML подтверждена pagination через `?p=N`, но нельзя гарантировать, что абсолютно все страницы сохраняют тот же DOM.

# 7. Порядок реализации

### 1. parser.py

Начать с parser, потому что его можно полностью тестировать на сохранённых HTML без сети.

Порядок:

- `parse_product()`;
- extraction основных полей;
- price handling;
- text cleaning;
- breadcrumb;
- image extraction;
- затем `Specs`/`Spec_detail`.
Это позволит сначала подтвердить правильность результата на fixtures.

### 2. scraper.py

После стабилизации parser реализовать:

- category navigation;
- extraction product URLs;
- переходы на product pages;
- pagination;
- retry;
- delays;
- image download side effect.

#!/usr/bin/env python3
# -*- coding: utf-8 -*-

import re
import time
import random
from datetime import datetime

def log_message(level: str, message: str) -> None:
    """
    Универсальный форматированный логгер для вывода в консоль.
    Заменяет тяжелые библиотеки логирования простым и понятным для ИИ кодом.
    """
    timestamp = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
    print(f"[{timestamp}] [{level.upper()}] {message}")

def random_delay(min_seconds: float = 1.0, max_seconds: float = 3.0) -> None:
    """
    Генерирует случайную паузу. Помогает имитировать поведение 
    реального пользователя и обходить базовые лимиты запросов (Rate Limiting).
    """
    delay = random.uniform(min_seconds, max_seconds)
    time.sleep(delay)

def clean_price(price_string: str) -> float:
    """
    Утилита очистки строки цены (например, '$1,299.99' или '150.00 €') 
    и конвертации её в чистое число с плавающей точкой (float).
    Очень частый запрос от клиентов на Upwork.
    """
    if not price_string:
        return 0.0
        
    try:
        # Удаляем все пробельные символы
        cleaned = re.sub(r"\s+", "", price_string)
        # Оставляем только цифры, точки и запятые
        cleaned = re.sub(r"[^\d.,]", "", cleaned)
        
        # Если в цене есть и точка, и запятая (например, 1,250.50)
        if "," in cleaned and "." in cleaned:
            # Если запятая идет первой, это разделитель тысяч (US стиль) -> просто убираем её
            if cleaned.find(",") < cleaned.find("."):
                cleaned = cleaned.replace(",", "")
            # Если точка идет первой (EU стиль, например, 1.250,50) -> убираем точку, запятую меняем на точку
            else:
                cleaned = cleaned.replace(".", "").replace(",", ".")
        # Если есть только запятая (EU стиль без копеек или с копейками через запятую: '150,50')
        elif "," in cleaned and "." not in cleaned:
            cleaned = cleaned.replace(",", ".")
            
        return float(cleaned)
    except Exception:
        # Если очистить не удалось, возвращаем 0.0, чтобы скрипт не падал
        return 0.0

### Как обходить страницы товаров (product pages)

Если по плану нужны данные со страниц отдельных товаров — **scraper.py сам извлекает URL товаров из HTML листинга** (это навигационная логика, не бизнес-парсинг) и добавляет HTML каждой product page в результирующий список.

```python
def scrape_data(engine) -> List[str]:
    raw_contents = []

    # 1. Обход листинговых страниц
    current_url = BASE_URL
    while current_url:
        engine.goto(current_url)
        listing_html = engine.content()

        # 2. Извлечь URL товаров — допустимо в scraper через BeautifulSoup/regex
        product_urls = _extract_product_urls(listing_html)

        # 3. Зайти на каждую страницу товара
        for url in product_urls:
            engine.goto(url)
            raw_contents.append(engine.content())  # HTML товара → в список

        # 4. Пагинация листинга
        current_url = _get_next_page_url(listing_html, current_url)

    return raw_contents  # List[str] — HTML страниц товаров
```

`parse_html_data` в `main.py` затем вызовет `parse_listing()` для каждого из этих HTML. Значит `parse_listing()` должен уметь парсить HTML страницы товара (а не только листинга). Убедись, что логика `parse_listing()` в плане соответствует тому, какой именно HTML будет ему передан.

**Если достаточно листинговых страниц** (все нужные данные есть на странице категории) — добавляй в список HTML листинга, не заходи на product pages.
