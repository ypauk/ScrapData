# КОНТЕКСТ ПРОЕКТА

## Анализ (этап 1)

## 1. Краткое описание задачи


Клиент хочет получить scraper для сайта Professionele-Koeling.nl, который собирает данные о товарах из категории **Koelkasten&Kisten**.


На текущем этапе требуется **не полный scrape**, а тестовая выгрузка **ровно 2 товаров**. Для каждого товара необходимо собрать все поля, предусмотренные `DS-PRK-Scraper.json`, включая:



- URL;

- Breadcrumb;

- название;

- краткое описание;

- изображения и их имена;

- обычную цену;

- цену со скидкой;

- полное описание;

- характеристики;

- детали характеристик.


Клиент отдельно указал, что:



- результат должен быть JSON;

- изображения необходимо **скачивать**, а не только сохранять URL;

- при отсутствии скидки `Sale price` оставляется пустым;

- отсутствующие характеристики оставляются пустыми;

- описание сохраняется как чистый текст, без HTML;

- товары без наличия также должны включаться;

- порядок и названия выходных полей должны строго соответствовать спецификации.


На самом сайте категория сейчас действительно содержит пагинацию: показывается **36 товаров из 429**, то есть для полного scrape потребуется обход нескольких страниц. Professionele Koeling


**Уверенность: высокая** — требования явно зафиксированы в предоставленном prompt и сопутствующих файлах. GitHub



## 2. Какой конечный результат нужен


Основной результат — **JSON-файл** с данными товаров.


На текущем этапе:



- только 2 товара;

- каждый товар — отдельная запись;

- все поля из `DS-PRK-Scraper.json`;

- каждое требуемое поле должно оставаться отдельным полем;

- структура и порядок полей не должны самовольно изменяться;

- изображения должны быть физически скачаны;

- отсутствующие значения — пустые поля.


Тестовый результат должен позволить клиенту проверить корректность структуры и качества данных до запуска полного scrape.



## 3. Как лучше решить задачу


### Рекомендация: PlaywrightEngine + парсинг HTML


Для данного проекта оптимален **Playwright**, который уже является обязательной частью предоставленного проектного фреймворка: prompt прямо указывает, что `scraper.py` получает готовый `PlaywrightEngine`.


Оптимальная логика на уровне подхода:



- Открывать страницу категории через Playwright.

- Получать ссылки на товары из карточек.

- Обходить pagination.

- Для каждого товара открывать product page.

- Из HTML извлекать необходимые поля.

- Скачивать изображения.

- Преобразовывать описание в чистый текст.

- Извлекать характеристики и разделять их согласно инструкции спецификации.

- Формировать JSON строго по `DS-PRK-Scraper.json`.

- Сначала экспортировать только 2 товара для проверки.


Это предпочтительнее попытки строить отдельный API-клиент: в предоставленных данных API не обнаружен, а `network.har` пуст.


При этом **не следует автоматически использовать браузер для всего процесса только ради JavaScript**. По доступному HTML видно, что карточки товаров, цены, ссылки и pagination уже присутствуют в HTML-ответе. Текущая страница отдаёт полноценный список товаров и ссылки на product pages. Professionele Koeling


**Уверенность: высокая.**



## 4. Почему остальные варианты хуже


### Requests + BeautifulSoup


Технически часть сайта, судя по полученному HTML, можно было бы парсить обычными HTTP-запросами. Однако это **не лучший вариант именно для данного проекта**, потому что:



- проектный фреймворк уже фиксирует `PlaywrightEngine`;

- в исходных заметках указано, что сайт работает с JS;

- потребуется учитывать cookies/Cloudflare;

- переход на другую технологию усложнит интеграцию с существующим scraper framework.


Поэтому не стоит менять зафиксированный механизм получения страниц без необходимости.


### Scrapy


Для 429 товаров Scrapy мог бы быть эффективным, но здесь это избыточно:



- нет необходимости строить отдельный crawling framework;

- уже есть PlaywrightEngine;

- объём относительно небольшой;

- текущая задача — сначала 2 товара.


### Selenium


Playwright современнее и уже предусмотрен проектом. Использование Selenium не даёт преимуществ.


### API


На основании предоставленных файлов API не найден. `network.har` пуст, а `notes.txt` прямо сообщает об отсутствии API. Поэтому проектировать API-интеграцию сейчас оснований нет.


### Только листинг без product pages


Это потенциально самое простое решение, но **для текущей спецификации недостаточное**. В карточке категории доступны название, ссылка, изображение и цены, тогда как подробное описание и характеристики находятся на странице товара. Предоставленный `product-page.html` это подтверждает. Professionele Koeling+1

## 7. Возможные сложности


### 1. Cloudflare


Наиболее существенный технический риск. В предоставленных cookies присутствует `cf_clearance`.

Сайт, судя по структуре HTML, использует достаточно традиционную e-commerce-разметку, но CSS-классы и DOM-структура всё равно могут измениться.

Не все товары обязательно имеют одинаковые:



- количество изображений;

### 6. Характеристики


Это наиболее неоднозначная часть спецификации.

То есть характеристики должны интерпретироваться как пары **название характеристики → значение**.


При этом `Specs` содержит дополнительную инструкцию о разделении данных по колонкам. Это необходимо строго сохранить при формировании результата и не заменять собственной моделью данных.

Это говорит о том, что в проекте уже существует механизм checkpoint/resume. Его поведение не следует менять на этапе анализа.

## 10. План разработки


### Этап 1 — анализ структуры страниц


**Цель:** окончательно определить источники всех полей.


**Ожидаемый результат:** для каждого поля спецификации определён источник на category/product page.


**Зависимости:** предоставленные HTML-файлы.



### Этап 2 — получение списка товаров


**Цель:** получать ссылки на product pages из категории.


**Ожидаемый результат:** корректный список URL товаров и корректная обработка pagination.


**Зависимости:** PlaywrightEngine.



### Этап 3 — извлечение данных товара


**Цель:** получить все поля из product page.


**Ожидаемый результат:** одна полностью заполненная запись товара, включая допустимые пустые поля.


**Зависимости:** этап 2.



### Этап 4 — обработка изображений


**Цель:** скачать все требуемые изображения и сформировать `imageurl`/`image_name` согласно спецификации.


**Ожидаемый результат:** изображения сохранены, а соответствующие значения записаны в JSON.


**Зависимости:** URL изображений из product page.



### Этап 5 — обработка характеристик


**Цель:** преобразовать характеристики в требуемую структуру без изменения исходной спецификации.


**Ожидаемый результат:** каждый параметр корректно отделён от значения, отсутствующие параметры остаются пустыми.


**Зависимости:** структура product page.



### Этап 6 — тестовая выгрузка


**Цель:** собрать ровно 2 товара.


**Ожидаемый результат:** валидный JSON с двумя товарами, включая изображения.


**Зависимости:** этапы 1–5.



### Этап 7 — проверка результата


**Цель:** сравнить тестовую выгрузку с `DS-PRK-Scraper.json`.


**Ожидаемый результат:** подтверждены названия, порядок и наличие всех требуемых полей.


**Зависимости:** тестовый JSON.



### Этап 8 — полный scrape


**Цель:** после подтверждения теста собрать весь необходимый объём.


**Ожидаемый результат:** полный JSON со всеми товарами.


**Зависимости:** одобрение тестовых 2 товаров клиентом.

## План проекта (этап 2)

## 1. Полный поток данных

Выбран **HTML + PlaywrightEngine**. API/GraphQL использовать не следует: в предоставленных материалах API не обнаружен, а HTML уже содержит необходимые данные. Playwright обязателен архитектурой проекта и подходит для обхода сайта с JavaScript/Cookies/Cloudflare.

Поток:

`https://www.professionele-koeling.nl/koelkasten-kisten.html`↓`PlaywrightEngine`↓HTML страницы категории↓из HTML извлекаются URL карточек товаров — только навигационная логика scraper↓страницы отдельных товаров через PlaywrightEngine↓`List[str]` с HTML product pages↓`main.py → parse_html_data(raw_pages_content)`↓`BeautifulSoup`↓`dict` для каждого товара↓`list[dict]`↓`exporter.py → save_to_json() / save_to_csv()`

Для тестового запуска scraper должен получить **2 товара**, но архитектура должна позволять после подтверждения клиента пройти всю категорию.

Предоставленная пагинация показывает стандартный параметр `?p=N`. При этом в данных указано 429 товаров и 36 товаров на странице, поэтому нельзя использовать старый `checkpoint.json` как источник актуального количества.

## Почему выбран HTML + Playwright

### Почему не API

В `network.har` отсутствуют данные, `notes.txt` прямо указывает на отсутствие API, а предоставленный анализ не обнаружил API/GraphQL.

**Плюсы отказа от API:**

- не требуется искать несуществующий API;
- данные уже доступны в HTML;
- решение соответствует имеющемуся framework.
### Почему Playwright

`main.py` зафиксирован на `PlaywrightEngine`, поэтому `scraper.py` должен принимать готовый `engine` и работать через него.

**Плюсы:**

- совместимость с существующим ядром;
- работа с Cookies;
- возможность переживать JavaScript-навигацию;
- возможность работать с Cloudflare/browser context;
- единый механизм загрузки страниц для проекта.
**Минусы:**

- тяжелее и медленнее обычного HTTP;
- возможны timeout/Cloudflare/CAPTCHA;
- браузер требуется для каждой сессии обхода.
`requests`/`httpx` в `scraper.py` не предлагаются, поскольку это нарушило бы установленный контракт framework.

# 2. Проектирование app/scraper.py

## 2.1. Интерфейс функций

### scrape_data(engine) → List[str]

**Назначение:** главная функция scraper, полностью совместимая с `main.py`.

**Вход:**

- `engine` — уже созданный `PlaywrightEngine`.
**Возвращает:**

- `List[str]`, где каждый элемент — HTML отдельной страницы товара.
Для тестового режима результат должен содержать HTML ровно двух product pages.

Важно: `scrape_data()` не должен возвращать словари и не должен вызывать функции `parser.py`.

### _fetch_listing_html(engine, url) → str

**Назначение:** открыть страницу категории и получить ее HTML.

**Вход:**

- `engine`;
- URL категории.
**Возвращает:**

- HTML страницы как `str`.
Перед получением HTML необходимо дождаться появления контейнера списка товаров.

Ожидаемый ориентир из предоставленного HTML:

- `.products-grid`
- `.products-grid .item`
Более конкретный известный из входных данных контейнер:

`ul.products-grid.category-products-grid.itemgrid.itemgrid-adaptive.itemgrid-3col.centered.hover-effect.equal-height`

Внутри него карточки представлены элементами `li.item`.

### _extract_product_urls(html) → List[str]

**Назначение:** извлечь URL товаров из HTML листинга.

Это допустимая логика в `scraper.py`, поскольку URL необходимы именно для дальнейшей навигации.

**Вход:**

- HTML категории.
**Возвращает:**

- список абсолютных product URL.
Из предоставленного HTML известен селектор:

`li.item a.product-image[href]`

Также допустим:

`li.item h2.product-name a[href]`

Лучше использовать ссылку из `.product-name`, либо проверить обе ссылки и дедуплицировать URL.

Пример подтвержденного URL:

`https://www.professionele-koeling.nl/koelkasten-kisten/polar-dm071.html`

### _fetch_product_html(engine, url) → str

**Назначение:** открыть product page и вернуть ее HTML.

**Вход:**

- `engine`;
- product URL.
**Возвращает:**

- HTML страницы товара.
Перед сохранением HTML необходимо дождаться основного product content. Из предоставленного HTML подтверждены:

- `.breadcrumbs`
- `.product-name h1`
- `.short-description`
- `.price-box`
Для полной страницы также требуется дождаться основного product container, если он имеется в реальном DOM.

### _get_next_page_url(html, current_url) → str | None

**Назначение:** определить следующую страницу категории.

В предоставленных данных подтверждена пагинация:

`https://www.professionele-koeling.nl/koelkasten-kisten.html?p=2`

и далее `?p=3`, `?p=4` и т. д.

Основной селектор:

`.pager .pages li.next a[href]`

Алгоритм:

- Найти `.pager .pages`.
- Найти ссылку `.next`.
- Если ссылка существует — вернуть ее абсолютный URL.
- Если ссылки нет — вернуть `None`.
- Не вычислять количество страниц самостоятельно, если сайт уже предоставляет ссылку Next.
## 2.2. Алгоритм обхода

### Тестовый режим

- Открыть категорию:`https://www.professionele-koeling.nl/koelkasten-kisten.html`
- Дождаться списка товаров.
- Получить URL карточек.
- Взять первые два уникальных URL.
- Открыть первый product page.
- Получить HTML.
- Выполнить `random_delay()`.
- Открыть второй product page.
- Получить HTML.
- Вернуть два HTML в `List[str]`.
Для тестового запуска нет необходимости обходить все 429 товаров.

### Полный режим

После одобрения тестового результата:

- открыть первую страницу;
- извлечь product URLs;
- пройти product pages;
- найти Next;
- перейти на следующую страницу;
- повторять до отсутствия Next;
- дедуплицировать product URLs;
- получить HTML каждой product page;
- вернуть список HTML товаров.
Не следует ориентироваться на `checkpoint.json`: он содержит старое состояние запуска и противоречит актуальным данным pagination (`processed_count=49` против показанных `429` товаров).

## Пагинация

Использовать **переход по URL**, а не infinite scroll и не клики по JavaScript-кнопкам.

Подтверждение из входных данных:

`?p=2`, `?p=3`, `?p=4`, `?p=5`.

Infinite scroll в анализе не обнаружен.

## Ожидание контента

Перед извлечением HTML листинга дождаться наличия:

`ul.products-grid`

и/или

`ul.products-grid li.item`.

Перед product page дождаться основных элементов:

- `.product-name h1`
- `.short-description`
- `.price-box`
Если один из необязательных блоков отсутствует, страница не должна автоматически считаться ошибочной: отсутствие конкретного поля обрабатывается parser.

## Lazy Loading / клики / scroll

По предоставленным материалам infinite scroll и необходимость специальных кликов не подтверждены.

Поэтому:

- специальный scroll не нужен;
- «Показать еще» не нужен;
- раскрытие tabs не проектируется без подтверждения наличия таких элементов;
- обычного открытия product page достаточно.
## random_delay()

Использовать уже существующий `app.utils.random_delay()`:

- между последовательными переходами на product pages;
- между переходами на страницы категории;
- после обнаружения Cloudflare/защитного поведения — только в рамках существующей сетевой политики проекта.
Не создавать собственную функцию задержки в `scraper.py`.

## 3.2. Спецификация полей

Итоговые названия должны сохраняться **буквально такими, как в **`DS-PRK-Scraper.json`, включая существующий trailing space в ключах `"Title "` и `"Description "`.

Порядок:

- `URL`
- `Breadcrumb`
- `Title `
- `Short description`
- `imageurl`
- `image_name`
- `Price`
- `Sale price`
- `Description `
- `Specs`
- `Spec_detail`
Никаких дополнительных полей добавлять нельзя.

### URL

Источник:

URL текущей product page.

Значение должно быть URL товара, а не URL категории.

**ПРЕДПОЛОЖЕНИЕ:** поскольку HTML product page в предоставленных материалах не содержит canonical URL, scraper/parser должен сохранить URL, по которому была открыта product page. Если контракт `List[str]` не позволяет передать URL отдельно от HTML, его необходимо получить из самого HTML только если соответствующий элемент присутствует. В противном случае архитектурный контракт не предоставляет parser надежного источника URL.

Это один из оставшихся неизвестных вопросов.

### Breadcrumb

Источник:

`.breadcrumbs`

Из предоставленного HTML:

- `Home`
- `Koelkasten&Kisten`
- название товара.
При этом в `DS-PRK-Scraper.json` образец имеет:

`"Breadcrumb": "Home"`

Поэтому нельзя самостоятельно расширять поле до всей цепочки. Авторитетная спецификация содержит именно `Home`.

**Правило:** не переинтерпретировать поле; если scraper/parser должен воспроизводить именно DS-PRK-Scraper.json, `Breadcrumb` должен быть `Home`.

### Title

Источник:

`.product-name h1`

Пример:

`Polar GE579`

Если отсутствует — `""`.

### Short description

Источник:

`.short-description .std`

HTML очищается до текста.

`<br>` преобразуется в перенос/разделитель whitespace, HTML-теги удаляются.

Не включать в short description рекламный блок с телефоном, если он является отдельным содержательным элементом страницы и не относится к описанию товара.

В предоставленном HTML основной текст находится в `<p>`, а рекламный блок — в `<h4>`.

### imageurl

Необходимо получить URL всех изображений товара.

Значения нескольких изображений объединяются **через запятую**, как прямо указано в DS:

`if multipli seperated by comma`

Изображения должны быть скачаны scraper-логикой/интеграционным процессом, но parser не должен выполнять сетевой download.

Критически важно: текущие входные данные не дают полного HTML блока галереи товара, поэтому точный селектор оригинальных product images неизвестен.

**ПРЕДПОЛОЖЕНИЕ:** на product page следует искать изображения основной галереи, а не ограничиваться thumbnail из category page.

### image_name

Соответствует скачанным изображениям.

Если несколько — имена через запятую.

Но правило формирования имени файла в спецификации отсутствует.

Поэтому конкретный naming convention нельзя выдумывать.

**ПРЕДПОЛОЖЕНИЕ:** имя может формироваться из исходного filename URL изображения с сохранением расширения, однако это требует подтверждения клиента/существующего framework.

### Price

Источник:

`.price-box .old-price .price`

Пример из предоставленного HTML:

`€ 255,99`

→ `255.99`

Для `Polar DM071`:

`€ 179,00` → `179.00`.

Следует использовать существующую `app.utils.clean_price()`, а не создавать новую функцию очистки цены.

Если обычная цена отсутствует — `""`.

### Sale price

Источник:

`.price-box .special-price .price`

Пример:

`€ 229,00` → `229.00`.

Если скидки нет — **пустое поле**, а не копирование обычной цены.

Это прямо указано в `notes.txt`.

### Description

Источник — основной description-блок product page.

HTML должен быть преобразован в чистый текст.

Не сохранять HTML-разметку.

Сохранять содержательную структуру текста: абзацы/переносы между логическими блоками должны оставаться читаемыми.

Предоставленный образец `DS-PRK-Scraper.json` подтверждает, что description может содержать:

- вводное описание;
- `Uitvoering`;
- `Specificaties`;
- дополнительные пояснения;
- `Gebruikertips`.
### Specs

Спецификация прямо говорит:

`evertything before the : is the header`

То есть для характеристики:

`Artikelnummer: GE579`

заголовок — `Artikelnummer`.

Для:

`Inhoud: 29 liter`

заголовок — `Inhoud`.

Однако **точный способ представления нескольких headers внутри одного JSON-поля **`Specs`** DS-PRK-Scraper.json не определяет**.

Поэтому нельзя самостоятельно выбирать JSON array, comma-separated string, object или отдельные динамические ключи.

Это должно оставаться согласно существующему exporter/schema contract.

### Spec_detail

Для тех же характеристик значение после `:` является detail/value.

Например концептуально:

`Artikelnummer: GE579`

→ header: `Artikelnummer`→ detail: `GE579`

Но способ упаковки нескольких значений в единственное поле `Spec_detail` также не задан однозначно.

**Важно:** не превращать каждую характеристику в новый top-level JSON key, поскольку это нарушит фиксированную структуру.

## 3.3. Финальная структура результата

Один record должен иметь только следующие ключи и именно в таком порядке:

```
{
    "URL": "...",
    "Breadcrumb": "...",
    "Title ": "...",
    "Short description": "...",
    "imageurl": "...",
    "image_name": "...",
    "Price": ...,
    "Sale price": ...,
    "Description ": "...",
    "Specs": "...",
    "Spec_detail": "..."
}
```

Это не готовый Python-код, а контракт структуры.

Для отсутствующих значений использовать пустые значения, поскольку это явно задано клиентом:

- отсутствующая скидка → `""`;
- отсутствующая характеристика → пустое поле;
- отсутствующее текстовое значение → `""`.
Товары без наличия не отбрасывать.

# 5. Оценка рисков

- **Cloudflare (защита)** — подтверждены признаки `cf_clearance`; риск средний/высокий.
- **Требуется авторизация (Login)** — по предоставленным данным не требуется.
- **Rate Limiting** — точные лимиты неизвестны.
- **CAPTCHA** — не подтверждена, но возможна при усилении защиты.
- **Infinite Scroll** — не обнаружен.
- **Shadow DOM** — не обнаружен.
- **iframe** — для требуемых данных не подтвержден.
- **WebSocket** — не обнаружен.
- **GraphQL API** — не обнаружен.
- **Сложная структура DOM с частыми изменениями** — потенциальный риск, поскольку scraper зависит от CSS-классов Magento-подобной разметки.
- **Изменение структуры изображений** — точный gallery HTML отсутствует.
- **Неопределенный формат Specs/Spec_detail** — главный функциональный риск.
- **Правило image_name** — не определено.
- **URL оригинальных изображений** — не подтвержден.
- **Различие thumbnail/original** — подтверждено наличием category thumbnail; оригинальная gallery-разметка не предоставлена.
# 6. Что останется неизвестным

После проектирования остаются следующие данные, которые нельзя достоверно восстановить из предоставленного prompt:

- **Точный HTML блока product gallery.**Входной `product-page.html` обрывается после блока цены, поэтому точные селекторы всех изображений неизвестны.
- **Какой именно URL изображения использовать в **`imageurl`**: thumbnail или original.**Для category page известен thumbnail URL, но требования требуют скачивать изображения, поэтому предпочтение original выглядит логичным, но это не подтверждено спецификацией.
- **Правило именования скачанных файлов **`image_name`**.**В prompt отсутствует конкретный naming convention.
- **Точная структура **`Specs`** и **`Spec_detail`**.**Известно только правило:

- до `:` — header;
- после `:` — detail/value.
Но не определено, как множество характеристик должно помещаться в два top-level JSON fields.
- **Источник **`URL`** внутри переданного HTML.**Входной контракт `scrape_data(engine) → List[str]` передает parser только HTML. Если product URL отсутствует внутри HTML, parser не может надежно восстановить его без изменения зафиксированного интерфейса.
- **Полная разметка Description.**Предоставленный product-page HTML содержит только часть страницы. Поэтому точный selector полного description-блока требует проверки сохраненного полного HTML.
- **Точная структура наличия товара.**Требование «включать товары без наличия» подтверждено, но отдельный availability field отсутствует в DS-PRK-Scraper.json, поэтому добавлять его нельзя.
### Не следует считать неизвестными

Не нужно дополнительно запрашивать:

- оригинальную Google Sheet;
- новую копию `DS-PRK-Scraper.json`;
- API;
- checkpoint как источник количества товаров.
Prompt прямо определяет `DS-PRK-Scraper.json` как окончательную спецификацию.

def log_message(level: str, message: str) -> None:
    """

def random_delay(min_seconds: float = 1.0, max_seconds: float = 3.0) -> None:
    """
    Генерирует случайную паузу. Помогает имитировать поведение 
    реального пользователя и обходить базовые лимиты запросов (Rate Limiting).
    """
    delay = random.uniform(min_seconds, max_seconds)
    time.sleep(delay)

def clean_price(price_string: str) -> float:
    """
    Утилита очистки строки цены (например, '$1,299.99' или '150.00 €') 
    и конвертации её в чистое число с плавающей точкой (float).
    Очень частый запрос от клиентов на Upwork.
    """
    if not price_string:
        return 0.0
        
    try:
        # Удаляем все пробельные символы
        cleaned = re.sub(r"\s+", "", price_string)
        # Оставляем только цифры, точки и запятые
        cleaned = re.sub(r"[^\d.,]", "", cleaned)
        
        # Если в цене есть и точка, и запятая (например, 1,250.50)
        if "," in cleaned and "." in cleaned:
            # Если запятая идет первой, это разделитель тысяч (US стиль) -> просто убираем её
            if cleaned.find(",") < cleaned.find("."):
                cleaned = cleaned.replace(",", "")
            # Если точка идет первой (EU стиль, например, 1.250,50) -> убираем точку, запятую меняем на точку
            else:
                cleaned = cleaned.replace(".", "").replace(",", ".")
        # Если есть только запятая (EU стиль без копеек или с копейками через запятую: '150,50')
        elif "," in cleaned and "." not in cleaned:
            cleaned = cleaned.replace(",", ".")
            
        return float(cleaned)
    except Exception:
        # Если очистить не удалось, возвращаем 0.0, чтобы скрипт не падал
        return 0.0

### Как обходить страницы товаров (product pages)

Если по плану нужны данные со страниц отдельных товаров — **scraper.py сам извлекает URL товаров из HTML листинга** (это навигационная логика, не бизнес-парсинг) и добавляет HTML каждой product page в результирующий список.

```python
def scrape_data(engine) -> List[str]:
    raw_contents = []

    # 1. Обход листинговых страниц
    current_url = BASE_URL
    while current_url:
        engine.goto(current_url)
        listing_html = engine.content()

        # 2. Извлечь URL товаров — допустимо в scraper через BeautifulSoup/regex
        product_urls = _extract_product_urls(listing_html)

        # 3. Зайти на каждую страницу товара
        for url in product_urls:
            engine.goto(url)
            raw_contents.append(engine.content())  # HTML товара → в список

        # 4. Пагинация листинга
        current_url = _get_next_page_url(listing_html, current_url)

    return raw_contents  # List[str] — HTML страниц товаров
```

`parse_html_data` в `main.py` затем вызовет `parse_listing()` для каждого из этих HTML. Значит `parse_listing()` должен уметь парсить HTML страницы товара (а не только листинга). Убедись, что логика `parse_listing()` в плане соответствует тому, какой именно HTML будет ему передан.

**Если достаточно листинговых страниц** (все нужные данные есть на странице категории) — добавляй в список HTML листинга, не заходи на product pages.
