# КОНТЕКСТ ПРОЕКТА

## Анализ (этап 1)

## 1. Краткое описание задачи

Клиент хочет получить scraper для сайта **professionele-koeling.nl**, который собирает данные о товарах из категории холодильного оборудования.

На текущем этапе требуется **не полный scrape**, а тестовая выгрузка только **2 товаров**. Для каждого товара необходимо собрать все поля, определённые в `DS-PRK-Scraper.json`, причём каждое поле должно находиться в отдельном JSON-поле и иметь стабильное имя.

Обязательные особенности:

- собрать URL товара и breadcrumb;
- название;
- короткое описание;
- изображения и их имена;
- обычную цену;
- цену со скидкой;
- полное текстовое описание без HTML;
- характеристики;
- отдельные значения характеристик;
- отсутствующие значения оставлять пустыми;
- товары без скидки не дублировать: `Sale price` должен быть пустым;
- включать товары, даже если они отсутствуют в наличии;
- изображения необходимо **скачивать**, а не только сохранять URL;
- порядок и названия полей должны строго соответствовать `DS-PRK-Scraper.json`.
`DS-PRK-Scraper.json` явно обозначен в исходном prompt как окончательная и авторитетная спецификация, поэтому его структуру нельзя самостоятельно изменять.

**Уверенность: высокая.**

## 2. Какой конечный результат нужен

Конечный результат — **JSON**.

На текущем этапе:

- JSON с данными 2 товаров.
- Скачанные изображения этих товаров.
- Поля JSON должны соответствовать структуре `DS-PRK-Scraper.json`.
В спецификации присутствуют следующие поля:

- `URL`
- `Breadcrumb`
- `Title `
- `Short description`
- `imageurl`
- `image_name`
- `Price`
- `Sale price`
- `Description `
- `Specs`
- `Spec_detail`
Особое внимание нужно уделить пробелам в названиях `Title ` и `Description `: поскольку спецификация объявлена авторитетной, **переименовывать их нельзя**.

**Уверенность: высокая.**

## 3. Как лучше решить задачу

Рекомендуемый подход — **Playwright + существующий PlaywrightEngine проекта + парсинг HTML средствами Python**.

Основная последовательность:

**категория → ссылки товаров → страницы товаров → извлечение данных → скачивание изображений → JSON.**

Почему именно так:

- в `notes.txt` прямо указано, что сайт работает с JavaScript;
- в prompt зафиксировано, что `scraper.py` уже получает готовый `PlaywrightEngine` из framework;
- поэтому использование браузера уже является частью инфраструктуры проекта и не требует добавления отдельной Selenium-архитектуры;
- HTML категории содержит ссылки на страницы товаров;
- HTML товара содержит breadcrumb, название, short description и цены;
- пагинация явно присутствует;
- для полного scrape потребуется обход страниц категории;
- для теста достаточно обработать первые 2 подходящих товара.
При этом не следует автоматически усложнять решение поиском API: в предоставленных материалах указано `API нет`, а `network.har` пустой. Поэтому на основании имеющихся данных наиболее простой путь — получать HTML через уже предоставленный PlaywrightEngine и извлекать данные из DOM.

**Уверенность: высокая для тестового scrape; средняя для полного сайта**, поскольку фактическая структура остальных товарных страниц не представлена.

## 4. Почему остальные варианты хуже

### Requests + BeautifulSoup

Не рекомендую как основной способ.

Причина: в материалах проекта прямо указано, что сайт использует JavaScript, а framework уже построен вокруг `PlaywrightEngine`. Кроме того, prompt отдельно запрещает считать рекомендацию `requests вместо Playwright` применимой в этом проекте.

### Selenium

Технически способен решить задачу, но не даёт преимуществ перед уже существующим PlaywrightEngine. Это будет ненужное усложнение.

### Scrapy

Для большого статического сайта мог бы быть хорошим вариантом, но здесь уже есть browser engine, а часть сайта потенциально зависит от JS. Введение Scrapy ради 429 товаров не выглядит оправданным.

### API

Предоставленные материалы не показывают доступного API. `network.har` пустой, а в `notes.txt` указано, что API нет.

Искать API специально можно было бы только при появлении новых доказательств его существования.

### GraphQL

Признаков GraphQL в предоставленных данных нет.

### Selenium/Playwright + отдельная API-архитектура

Избыточно: сейчас нет подтверждения, что API вообще существует.

**Вывод:** использовать уже имеющийся PlaywrightEngine и максимально простой DOM parsing.

## 7. Возможные сложности

### 1. Cloudflare

Наличие `cf_clearance` означает потенциальную защиту от автоматизированного доступа.

Риск особенно возрастает при:

- высокой частоте запросов;
- большом количестве параллельных страниц;
- повторных запусках;
- отсутствии нормального browser context.
### 2. JavaScript

Некоторые данные могут появляться или изменяться после выполнения JS.

Поэтому HTML, полученный обычным HTTP-запросом, нельзя считать гарантированно достаточным для всех страниц.

### 3. Изменение HTML

Селекторы основаны на текущей структуре сайта. При изменении frontend потребуется адаптация scraper.

### 4. Характеристики

`Specs` и `Spec_detail` требуют аккуратного преобразования данных.

Особенно важно не смешивать несколько характеристик в одной колонке, поскольку клиент отдельно требует: **каждое поле в отдельной колонке**.

### 5. Разные шаблоны товаров

Предоставлен только один пример product page. Нельзя гарантировать, что все 429 товаров имеют абсолютно одинаковый HTML.

### 6. Изображения

У одного товара может быть несколько изображений. В спецификации явно указано разделять несколько значений запятыми.

Кроме того, изображения нужно не просто извлечь, но и скачать.

### 7. Pagination

Для полного scrape потребуется пройти все страницы категории. Сейчас обнаружено 429 товаров при 36 товарах на страницу, то есть объём уже значительно больше тестовых двух товаров.

### 8. Цены

Нужно корректно различать:

- обычную цену;
- sale price;
- отсутствие скидки.
По правилам проекта при отсутствии скидки `Sale price` должен оставаться пустым.

### 9. Товары без наличия

Такие товары **необходимо включать**, поэтому нельзя фильтровать каталог только по availability.

## 8. Что нужно уточнить у клиента

Большинство вопросов уже закрыты в `answers.txt`, поэтому не нужно повторно спрашивать клиента о категориях, количестве тестовых товаров, скидках, изображениях, HTML или отсутствии характеристик.

Остаются только вопросы, которые действительно не определены однозначно.

### Вопрос 1 — структура JSON

Нужно уточнить, должен ли итоговый JSON быть:

- массивом объектов товаров;
- объектом с массивом товаров;
- либо последовательностью отдельных JSON-объектов.
В предоставленной спецификации показан один объект товара, но формат контейнера для нескольких товаров явно не определён.

### Вопрос 2 — imageurl

Нужно уточнить, что именно должно находиться в `imageurl` после требования скачать изображения:

- исходный URL сайта;
- локальный путь;
- или URL + локальный путь в разных полях.

Нужно уточнить ожидаемую структуру `Specs` в JSON, если клиент ожидает именно отдельные значения, а не одно текстовое поле.

При этом `Spec_detail` явно описывает правило: всё до `:` является header. Это нужно сохранить без переинтерпретации.

**Если клиент подтверждает эти три пункта, дополнительных блокирующих вопросов для тестовой реализации нет.**

## 10. План разработки

### Этап 1 — Проверка тестового сценария

**Цель:** получить две страницы товаров из категории.

**Ожидаемый результат:** корректно открываются страницы и извлекается HTML.

**Зависимости:** существующий PlaywrightEngine.

### Этап 2 — Извлечение основных полей

**Цель:** получить URL, breadcrumb, title, short description, цены и description.

**Ожидаемый результат:** все соответствующие поля заполнены согласно `DS-PRK-Scraper.json`.

**Зависимости:** HTML product page.

### Этап 3 — Извлечение характеристик

**Цель:** преобразовать характеристики в требуемый формат без смешивания разных данных.

**Ожидаемый результат:** `Specs` и `Spec_detail` соответствуют финальной спецификации.

**Зависимости:** подтверждение фактической структуры характеристик на тестовых товарах.

### Этап 4 — Изображения

**Цель:** найти все необходимые изображения и скачать их.

**Ожидаемый результат:** изображения физически сохранены, а `imageurl`/`image_name` заполнены согласно спецификации.

**Зависимости:** уточнение формата локальных ссылок/имён, если он не определён framework.

### Этап 5 — JSON для двух товаров

**Цель:** сформировать тестовую выгрузку.

**Ожидаемый результат:** JSON с двумя товарами, строго соответствующий структуре спецификации.

**Зависимости:** завершение предыдущих этапов.

### Этап 6 — Проверка

**Цель:** убедиться, что нет смешанных колонок/полей, пропущенных обязательных данных или неправильной обработки скидок.

**Ожидаемый результат:** готовый тестовый файл для отправки клиенту.

**Зависимости:** готовый JSON.

### Этап 7 — Full scrape после подтверждения теста

**Цель:** масштабировать проверенное решение на весь необходимый объём.

**Ожидаемый результат:** обработка всех требуемых товаров с pagination.

**Зависимости:** подтверждение клиентом тестового файла и отсутствие замечаний.

**Можно переходить к разработке тестового scraper после уточнения этих неоднозначных моментов. Код на данном этапе намеренно не приводится, поскольку исходный prompt прямо запрещает переходить к реализации.**

**Итог:** проект относительно простой по parsing, но имеет средний operational risk из-за JavaScript и Cloudflare. Для теста из 2 товаров оптимально не строить ничего сложного: сначала подтвердить корректность извлечения всех полей и изображений, затем масштабировать тот же подход на весь каталог.

# 2. Почему выбран Playwright + HTML

## Почему не API

API использовать не следует.

В предоставленных входных данных прямо указано, что API нет, а `network.har` пуст. Подтверждения REST/GraphQL API отсутствуют. Поэтому проектирование вокруг API потребовало бы выдумывать несуществующий интерфейс.

## Почему Playwright

Playwright является обязательным механизмом получения данных в данном проекте: `main.py` уже передаёт готовый `PlaywrightEngine` в `scrape_data(engine)`.

Кроме того:

- сайт использует JavaScript;
- в проект уже передаются cookies;
- присутствует `cf_clearance`;
- данные product page доступны после загрузки страницы;
- отдельные страницы товаров действительно содержат нужные поля;
- изображения потенциально требуют браузерного контекста.
Поэтому переход на `requests`/`httpx` противоречил бы архитектуре проекта и не даёт преимуществ.

## Почему HTML + BeautifulSoup

Основные данные находятся непосредственно в DOM:

- breadcrumb;
- title;
- short description;
- цены;
- описание;
- характеристики;
- изображения.
Следовательно, после получения HTML нет необходимости имитировать клики по каждому элементу или искать внутренние API.

### Плюсы

- полностью соответствует существующему framework;
- не требует нового сетевого слоя;
- хорошо отделяет получение HTML от его обработки;
- легко тестировать parser на сохранённых HTML;
- подходит как для тестовых 2 товаров, так и для полного scrape;
- минимальная архитектурная сложность.
### Минусы

- изменение HTML-селекторов может потребовать обновления parser;
- Cloudflare может сделать браузерный доступ нестабильным;
- структура галереи изображений требует отдельной проверки;
- cookies `cf_clearance` не являются гарантированным постоянным решением.

# 6. Спецификация полей

## URL

Источник:

`canonical URL` product page либо URL, по которому scraper открыл товар.

Для текущих страниц это URL вида:

`https://www.professionele-koeling.nl/koelkasten-kisten/polar-dm071.html`

Если canonical URL присутствует, предпочтительно использовать его как наиболее устойчивый источник.

## Breadcrumb

В HTML:

`.breadcrumbs`

Извлекать breadcrumb как текстовую структуру страницы.

В предоставленном product HTML фактически присутствуют:

`Home → Koelkasten&Kisten → Polar GE579`.

При этом в `DS-PRK-Scraper.json` пример значения для `Breadcrumb` — `Home`.

**ПРЕДПОЛОЖЕНИЕ:** итоговое значение должно соответствовать именно формату, заданному authoritative JSON, поэтому нельзя самостоятельно превращать его в новый формат `Home > Koelkasten&Kisten > Product`. Точный способ сериализации breadcrumb необходимо оставить в соответствии с существующей спецификацией.

## Title

Селектор:

`.product-name h1`

Извлечь текст и очистить окружающие пробелы.

Пример:

`Polar GE579`.

## Short description

Селектор:

`.short-description`

Нужно получить чистый текст.

HTML-теги (`br`, `p`, `strong` и т. п.) не должны попадать в итоговое значение.

Не следует включать в short description рекламный блок `Advies nodig...`, если authoritative specification подразумевает именно product short description. В предоставленном HTML этот блок находится внутри `.short-description`, поэтому его необходимо исключить по DOM-структуре, а не просто брать весь `.get_text()`.

**ПРЕДПОЛОЖЕНИЕ:** рекламный блок не относится к значению `Short description`; это следует дополнительно подтвердить на реальном полном HTML, если структура может отличаться.

## imageurl

Нужно собрать **все изображения товара**, а не только thumbnail из карточки категории.

Приоритет источников:

- оригинальный URL из атрибута zoom/full-size;
- `data-src`/аналогичный lazy-load URL;
- обычный `src`.
Не использовать thumbnail URL категории, если product page предоставляет оригинальное изображение.

Несколько URL сохранять согласно инструкции JSON: через запятую.

## image_name

Для каждого изображения определить имя файла из оригинального URL/DOM.

Например, если URL заканчивается:

`polar_ge579.jpg`

то имя — `polar_ge579.jpg`.

Несколько имён — через запятую в том же порядке, что и `imageurl`.

**ПРЕДПОЛОЖЕНИЕ:** именно имя файла из URL является ожидаемым значением, поскольку prompt не задаёт отдельного правила генерации имён.

## Price

В HTML цены различаются:

- `old-price` → обычная цена;
- `special-price` → sale price.
Для GE579 предоставленный HTML показывает `€255,99` как `old-price` и `€229,00` как `special-price`.

Следовательно:

`Price = 255.99`

`Sale price = 229.00`

Нужно использовать существующую `clean_price()` из `app.utils`, а не создавать второй механизм очистки цены.

## Sale price

Источник:

`.special-price .price`

Если `.special-price` отсутствует:

`Sale price = ""`

Именно пустая строка, а не копирование `Price`, согласно требованиям клиента.

## Description

Источник — основной блок полного product description.

Не включать:

- breadcrumb;
- цену;
- short description;
- reviews;
- форму отзыва;
- рекламные элементы, не являющиеся описанием товара.
Результат — **plain text**, без HTML.

Нужно сохранять логические переносы строк, чтобы списки `Uitvoering`, `Specificaties`, `Gebruikertips` и подобные секции не превращались в одну нечитаемую строку.

## Specs

Извлечь блок характеристик товара согласно точной структуре `DS-PRK-Scraper.json`.

Нельзя:

- объединять разные характеристики в произвольную одну колонку;
- создавать новые поля;
- переименовывать поля;
- интерпретировать отсутствующие значения.
Это особенно важно, поскольку набор характеристик у товаров различается.

## Spec_detail

В authoritative specification присутствует инструкция:

`everything before the : is the header`

Следовательно, для строки характеристики вида:

`Artikelnummer: GE579`

часть до `:`:

`Artikelnummer`

является именем/header характеристики, а часть после `:` — её значением.

Аналогично:

`Inhoud: 29 liter`

→ header: `Inhoud`

→ value: `29 liter`

Нельзя заранее фиксировать список возможных характеристик, поскольку у разных товаров набор различается.

**ПРЕДПОЛОЖЕНИЕ:** если итоговая экспортная схема требует фиксированных отдельных колонок для конкретных `Spec_detail`, их точные имена должны браться только из уже существующего authoritative `DS-PRK-Scraper.json`; parser не должен самостоятельно расширять схему на основании встретившихся характеристик.

# 7. Финальная структура результата

Каждый товар должен иметь только фиксированную структуру:

```
{
    "URL": ...,
    "Breadcrumb": ...,
    "Title ": ...,
    "Short description": ...,
    "imageurl": ...,
    "image_name": ...,
    "Price": ...,
    "Sale price": ...,
    "Description ": ...,
    "Specs": ...,
    "Spec_detail": ...
}
```

Это не готовый Python-код, а логическая схема результата.

Для отсутствующих данных:

- `Sale price` → `""`;
- отсутствующая характеристика → пустое значение;
- отсутствующее необязательное изображение → не добавлять выдуманный URL;
- отсутствующее текстовое значение → пустое значение в соответствии с форматом экспортера.
Нельзя добавлять, например, `sku`, `currency`, `availability`, `brand` и другие поля, даже если они обнаружены на странице.

# 9. Оценка рисков

- **Cloudflare** — средний/высокий риск. В cookies присутствует `cf_clearance`.
- **Авторизация** — не требуется для product pages.
- **Rate limiting** — точный лимит неизвестен; применять умеренные задержки.
- **CAPTCHA** — присутствует reCAPTCHA в форме отзывов, но это не означает CAPTCHA на обычном просмотре товара.
- **Infinite Scroll** — признаков нет.
- **Shadow DOM** — не обнаружен.
- **iframe** — для основных product data не требуется.
- **WebSocket** — не подтверждён.
- **GraphQL API** — не обнаружен.
- **Изменение DOM** — средний риск.
- **Изображения** — средний риск: необходимо отличать thumbnail от оригинального файла.
- **Различающиеся Specs** — средний риск: нельзя предполагать одинаковый набор характеристик.
- **Cookie expiration** — `cf_clearance` и другие cookies не следует считать постоянными.
- **Цена** — необходимо правильно различать `Van`/`old-price` и `Voor`/`special-price`.
# 10. Что остаётся неизвестным

Согласно предоставленным материалам, **блокирующих бизнес-вопросов нет**.

Остаются технические неопределённости:

- Точный DOM полной галереи изображений не представлен в сжатом `product-page.html`.
- Не подтверждено, какой атрибут содержит оригинальный image URL, если одновременно существуют thumbnail и full-size варианты.
- Не подтверждено точное правило формирования `image_name`, кроме очевидного варианта брать имя файла из URL.
- Не показана полная DOM-структура блока `Specs`.
- Не показан полный набор возможных `Spec_detail`.
- Не определён отдельный механизм физического сохранения изображений в фиксированном контракте `scrape_data(engine) → List[str]`.
Последний пункт особенно важен: требование клиента «скачивать изображения» существует, но установленный контракт передаёт между scraper/parser только HTML. Поэтому **нельзя самостоятельно изменять **`main.py`** или придумывать новый контракт**. Перед реализацией необходимо проверить, предусмотрено ли существующим ядром сохранение файлов либо соответствующая логика должна находиться в одном из уже существующих модулей.

**ПРЕДПОЛОЖЕНИЕ:** если существующее ядро не имеет механизма передачи/сохранения изображений, это является архитектурным несоответствием между бизнес-требованием и зафиксированным контрактом, которое нельзя исправлять изменением `main.py` в рамках данной задачи.

# 11. Порядок реализации

### 1. parser.py

Сначала спроектировать parser.

Причина: parser не зависит от сети и может тестироваться на предоставленных HTML.

Проверить:

- title;
- breadcrumb;
- short description;
- price;
- sale price;
- description;
- specs;
- изображения;
- отсутствие значений;
- точность имён и порядка полей.
### 2. scraper.py

После определения структуры parser реализовать сетевой сбор:

`category → product URLs → product pages`.

Причина: после фиксации ожидаемого набора product HTML проще определить, какие страницы scraper обязан вернуть.

### 3. Интеграция

Подключение к существующему `main.py` не требует его изменения:

`scrape_data(engine) → List[str]`

затем существующий orchestrator вызывает parser.

### 4. Тесты parser

Использовать сохранённые HTML как fixtures.

Минимальные тесты:

- обычный товар со скидкой;
- товар без скидки;
- несколько изображений;
- отсутствие изображений;
- отсутствие отдельных Specs;
- разные наборы Specs;
- HTML с рекламным блоком внутри short description;
- корректное преобразование цены;
- сохранение точного порядка полей.
### 5. Тест scraper

Проверить:

- открытие категории;
- извлечение уникальных product URLs;
- ограничение двумя товарами для текущего запуска;
- переход на product pages;
- получение непустого HTML;
- корректное поведение timeout/403.
### 6. Интеграционный тест

Получить ровно два товара и передать результаты существующему exporter.

Финальная проверка должна подтвердить:

- ровно 2 объекта;
- никаких дополнительных полей;
- нет пропущенных обязательных полей;
- порядок полей соответствует specification;
- `Sale price` пустой, если скидки нет;
- отсутствующие Specs не заменяются выдуманными значениями;
- description является plain text.
# 12. Краткое резюме

**Технология:** предоставляемый проектом `PlaywrightEngine` для навигации + HTML + BeautifulSoup для парсинга.

`scraper.py`**:**

- `scrape_data(engine)`
- `_fetch_listing_html(engine, url)`
- `_fetch_product_html(engine, url)`
- `_extract_product_urls(html)`
- `_get_next_page_url(html, current_url)`
Основная логика:

`category → URLs → 2 product pages → List[str]`.

`parser.py`**:**

- `parse_html_data(raw_pages_content)`
- `parse_product(html)`
- специализированные функции извлечения breadcrumb/title/description/images/prices/specs.
Parser не выполняет сетевых запросов.

**Итоговая структура:** строго поля `DS-PRK-Scraper.json` — `URL`, `Breadcrumb`, `Title `, `Short description`, `imageurl`, `image_name`, `Price`, `Sale price`, `Description `, `Specs`, `Spec_detail`. Никаких новых колонок.

**Главные риски:** Cloudflare/cookies, структура галереи изображений, физическое сохранение изображений при неизменяемом контракте `scrape_data()`, изменение DOM и неодинаковые наборы характеристик.

**Вывод:** задачу можно реализовать без изменения `main.py`, `browser.py`, `config.py`, `utils.py` и `exporter.py`, если существующее ядро уже предоставляет предусмотренный механизм сохранения изображений.     print(f"[{timestamp}] [{level.upper()}] {message}")

def random_delay(min_seconds: float = 1.0, max_seconds: float = 3.0) -> None:
    """
    Генерирует случайную паузу. Помогает имитировать поведение 
    реального пользователя и обходить базовые лимиты запросов (Rate Limiting).
    """
    delay = random.uniform(min_seconds, max_seconds)
    time.sleep(delay)

def clean_price(price_string: str) -> float:
    """
    Утилита очистки строки цены (например, '$1,299.99' или '150.00 €') 
    и конвертации её в чистое число с плавающей точкой (float).
    Очень частый запрос от клиентов на Upwork.
    """
    if not price_string:
        return 0.0
        
    try:
        # Удаляем все пробельные символы
        cleaned = re.sub(r"\s+", "", price_string)
        # Оставляем только цифры, точки и запятые
        cleaned = re.sub(r"[^\d.,]", "", cleaned)
        
        # Если в цене есть и точка, и запятая (например, 1,250.50)
        if "," in cleaned and "." in cleaned:
            # Если запятая идет первой, это разделитель тысяч (US стиль) -> просто убираем её
            if cleaned.find(",") < cleaned.find("."):
                cleaned = cleaned.replace(",", "")
            # Если точка идет первой (EU стиль, например, 1.250,50) -> убираем точку, запятую меняем на точку
            else:
                cleaned = cleaned.replace(".", "").replace(",", ".")
        # Если есть только запятая (EU стиль без копеек или с копейками через запятую: '150,50')
        elif "," in cleaned and "." not in cleaned:
            cleaned = cleaned.replace(",", ".")
            
        return float(cleaned)
    except Exception:
        # Если очистить не удалось, возвращаем 0.0, чтобы скрипт не падал
        return 0.0

### Как обходить страницы товаров (product pages)

Если по плану нужны данные со страниц отдельных товаров — **scraper.py сам извлекает URL товаров из HTML листинга** (это навигационная логика, не бизнес-парсинг) и добавляет HTML каждой product page в результирующий список.

```python
def scrape_data(engine) -> List[str]:
    raw_contents = []

    # 1. Обход листинговых страниц
    current_url = BASE_URL
    while current_url:
        engine.goto(current_url)
        listing_html = engine.content()

        # 2. Извлечь URL товаров — допустимо в scraper через BeautifulSoup/regex
        product_urls = _extract_product_urls(listing_html)

        # 3. Зайти на каждую страницу товара
        for url in product_urls:
            engine.goto(url)
            raw_contents.append(engine.content())  # HTML товара → в список

        # 4. Пагинация листинга
        current_url = _get_next_page_url(listing_html, current_url)

    return raw_contents  # List[str] — HTML страниц товаров
```

`parse_html_data` в `main.py` затем вызовет `parse_listing()` для каждого из этих HTML. Значит `parse_listing()` должен уметь парсить HTML страницы товара (а не только листинга). Убедись, что логика `parse_listing()` в плане соответствует тому, какой именно HTML будет ему передан.
